Reorg-safe event indexer

Stack
Node.js · Kafka · PostgreSQL · Redis
Surface
EVM logs → derived state → query API
Hard part
Being wrong is worse than being late

01 — The problem

Chain data is not final when you first see it. A block that exists now can be orphaned a few seconds later, and every row you derived from it becomes fiction. An indexer that treats a recent block as settled is a bug waiting for a reorg.

The failure is asymmetric. If a deposit is credited late, a user complains. If it is credited from a block that then disappears, the ledger is short and nobody finds out until reconciliation. One direction is recoverable, the other costs money.

02 — Approach

Three decisions carry most of the weight.

Verify the chain, not the number. Every ingested block carries its parent hash. Before applying it, the indexer checks that parent against the block it already has at that height. A mismatch means a fork, detected at ingestion instead of at reconciliation.

Make reverting a delete. Entities are stored as versions keyed by the block range they were valid for, rather than as mutable rows. Undoing a fork becomes deleting every version whose range opens after the fork point — no compensating updates, no repair logic to get subtly wrong.

Tier confirmations by value. A small transfer clears after a few confirmations. A large one waits for finality. The confirmation policy is a function of amount, not a single global constant, because the cost of being wrong is not uniform.

03 — Trade-offs

Large deposits settle noticeably slower, and that is a product decision as much as a technical one — it has to be explained to whoever owns the user experience.

The version-range schema is heavier than a flat table: more rows, more storage, and queries need a point-in-time predicate rather than a plain select. In exchange, time-travel queries come free and reorg handling stops being special-case code.

What I would not do again: treating the reorg path as an edge case to handle later. It has to be in the schema from the first migration, because retrofitting rollback onto mutable rows means rewriting the data model under a live system.
