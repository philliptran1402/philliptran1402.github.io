Oracles: push versus pull

Why the update model changes your liquidation design.

    DON ──▶ writes on-chain
  pull (Pyth)
    Hermes ──▶ you submit
    + confidence interval

How the update model reshapes the consumer
Watch for
Staleness, and ignoring confidence

01 — Two different shapes

Chainlink pushes: a decentralized oracle network aggregates off-chain, and nodes write the price on-chain when it deviates past a threshold or a heartbeat elapses. Reading is free and the value is simply there — possibly slightly old.

Pyth pulls: first-party publishers submit prices to an appchain at sub-second frequency, but nothing reaches your chain until a consumer fetches a signed update from Hermes and submits it, paying the gas, typically in the same transaction as the action that uses it.

02 — Why it changes your architecture

With push, the natural design is a poller and a cache: read the feed, store it, let the engine consume it. With pull there is nothing to poll — the update fetch belongs inline with the transaction, as close to execution as possible. The same liquidation bot is structured differently depending on which you use.

Pyth also returns a confidence interval alongside the price. Used properly, a widening interval is a signal to be more conservative — exactly when publishers disagree, which is exactly when markets are violent. Ignoring it throws away the most useful field in the response.

03 — The failure modes to design around

Staleness is the shared risk and it is silent: an old price is still a number. Chainlink consumers must check the round timestamp themselves; Pyth ships a built-in guard via a max-age parameter that reverts instead of returning something stale.

Both have a trust layer worth naming: a decentralized node network for one, and for the other an attestation path that is not operated by the oracle project itself. An oracle is a ceiling on how safe a lending or perp protocol can be — no downstream design compensates for a price that is wrong.
