01 — What it is

Concurrency bugs are the class that is hard to reproduce and easy to lose money on. These labs reproduce them on demand instead of waiting for production to do it.

The Go side covers data races caught by the race detector, goroutine leaks measured against a baseline goroutine count, and four shapes of deadlock — including one in a separate binary that genuinely crashes with all goroutines are asleep.

02 — The comparison that makes it worth doing

The Rust labs implement the same data race, and the point is where it is caught. Go finds it at runtime, with the race detector, and only if a test happens to exercise the bad interleaving. Rust refuses to compile it.

The Rust tests assert that refusal explicitly — compile_fail doctests proving the borrow checker rejects use-after-move, two mutable borrows, and sending a non-Send type across threads. A test that asserts code does not compile is an unusual and very direct way to document a language guarantee.

03 — Why it matters for money systems

A race on a balance update is not a flaky test, it is an incorrect ledger. Having a deterministic reproduction of each failure shape — and knowing which language catches which class, and when — changes how you review concurrent code rather than just how you debug it.
