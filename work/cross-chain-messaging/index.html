Question
Who is allowed to assert what happened elsewhere?

01 — The first-principles problem

Two chains cannot read each other's state. Any cross-chain message therefore reduces to one question: who is allowed to assert that something happened on chain A, and under what conditions does chain B believe them? Every bridge design is an answer to that, and most bridge failures are the answer being weaker than advertised.

02 — The architecture

An application contract talks to an Endpoint on each chain. Verification is performed by DVNs — decentralized verifier networks — in an M-of-N configuration the application itself chooses. Delivery is performed separately by an Executor.

Splitting verification from execution is the design's core insight. A message can be verified but undelivered — the Executor being unavailable is an inconvenience, not a loss of safety — and delivery can be retried without repeating verification.

Per-pathway configuration sets how many source-chain confirmations are required before a message is considered verifiable, which is the cross-chain equivalent of a finality tier.

03 — Where it can still go wrong

The application chooses its DVN set, so the security of a given pathway is the security of that choice — a cheap single-verifier configuration is a single point of trust wearing decentralized clothing. This is configuration, not protocol, and it is the first thing to inspect when evaluating an integration.

Replay protection comes from nonces and a per-message identifier; ordering guarantees are per-pathway, not global. Any token transfer built on top must have a conservation invariant that can be reconciled independently, because "the message said so" is not an accounting record.
