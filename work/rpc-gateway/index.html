Infrastructure · Reliability

RPC gateway with head-lag detection

Detect the lie, not the consequence. Refuse rather than serve stale.

  app ──▶ gateway
           ├─ probe head
           ├─ lag > N? skip
           ├─ 5xx? failover
           └─ getLogs cap
          ▼ freshest node
Stack
Go standard library · Docker · anvil
Surface
One internal URL for every service
Hard part
A lying upstream returns HTTP 200

01 — The problem

A single RPC URL is an invisible trust boundary. Every service reads chain state through it, and it can be wrong in a way that looks exactly like being right.

A provider serving a head from forty minutes ago does not return an error. It returns stale truth with a 200, and every consumer downstream acts on it confidently. Meanwhile the bill grows in ways nobody predicted, because eth_getLogs is priced per compute unit and one careless backfill range can cost more than a month of node hosting.

02 — Approach

Every service talks to one internal gateway instead of a provider URL, and the gateway owns all the policy that would otherwise be copy-pasted into each client.

It probes each upstream's head on a short interval and marks any source more than N blocks behind the best as lagging — a source that is up but behind is treated as unavailable, because for reading money it is. It fails over on 5xx and timeouts, caps eth_getLogs block ranges before they reach a node, allowlists methods so admin_ and debug_ can never be reached from outside, and rate-limits with a token bucket so one buggy loop cannot take down the node.

The decision worth arguing about: when only lagging sources remain, it refuses to answer. For a bot that signs transactions, an error is recoverable and a stale answer is not.

03 — Trade-offs

An extra network hop on every call, and a new component that itself has to be operated, monitored and kept available — the gateway is now a dependency of everything.

Bought: the ability to detect the lie instead of discovering the consequence, plus a single place to change provider mix, limits and caching without touching service code.

There is a runnable version of this with deterministic tests — fake upstreams and an injected clock, so lag detection and failover are tested without waiting on real chain timing.
