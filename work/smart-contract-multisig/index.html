01 — Proxy and singleton

Logic lives in one audited singleton deployed once per network. Each user's Safe is a minimal proxy that delegatecalls into it while keeping its own storage — owners, threshold, nonce, modules, guard. Creating a Safe is therefore cheap, and every Safe on a given version shares one well-reviewed implementation.

02 — Verification happens on-chain

Signatures are collected off-chain and checked on-chain in a single execute call. Three signature kinds are accepted: standard EIP-712 signatures, a pre-approved hash recorded by an owner, and a contract signature via EIP-1271 — which is how a Safe can be an owner of another Safe.

Off-chain coordination (the Transaction Service) stores pending transactions and collects approvals, but it is explicitly not the source of truth. Only the contract decides whether a transaction is authorised.

03 — Modules and Guards — the parts that surprise people

A Module is a contract authorised to execute through the Safe while bypassing the threshold check entirely. That is the feature — it is how spending limits, recurring payments, recovery flows and session keys are built — and it is also the part most people miss when they assume M-of-N covers every path. Auditing a Safe means auditing its modules.

A Guard runs before and after every transaction on the normal signing path and can revert even when signatures are valid, which is where automated policy belongs.

04 — The failure mode that matters

Ronin showed enough valid signatures controlled by too few parties. Bybit showed something sharper: no key broken, signatures valid, but the interface showed signers one transaction while their devices signed another hash. A multisig protects against a stolen key, not against every signer being shown the same lie. Verifying the hash independently of the interface proposing it is the control that closes that gap.
