RPC gateway lab

Go gateway plus two anvil nodes at different block times, so lag detection has something to detect.

Proves

01 — What it is

A working JSON-RPC gateway in Go, with a compose file that brings up two anvil nodes on different block times — one fast, one deliberately slow — so head-lag detection has a real gap to find rather than a mocked one.

No external Go dependencies. The whole thing is standard library, which keeps the test surface honest.

02 — What the tests prove

Seven tests, each asserting one property rather than exercising a happy path:

• admin_* is rejected before reaching any upstream — verified by asserting zero upstream hits, not just an error response.
• A 500 from the primary fails over to the secondary, and the fallback is counted.
• Given heads of 100 and 120 with a threshold of 5, the lagging node is marked and traffic routes to the fresh one.
• A 65 536-block eth_getLogs range is refused before it reaches a node; a 256-block range passes.
• Three eth_chainId calls produce one upstream hit and two cache hits.
• A burst of three passes and the fourth returns 429, then a refill lets the next through — using an injected clock, so there is no sleeping in tests.
• /health reports probed heights and flags.

03 — The part worth copying

The rate limiter takes its clock as a dependency. That one decision is why the test suite is deterministic and finishes in about a second and a half instead of being a flaky timing test. Anything that reads wall-clock time in production should read an injected clock in tests, and concurrency tests are where that pays off most.

The failover drill is also worth running by hand: stop the primary container, watch the health endpoint flip, then start it again and watch the freshly restarted node be marked as lagging — because a node that just came back is the oldest one in the pool.
