01 — Approach

Design for the failure case

Because the happy path was never the hard part

Money-path systems fail differently from product systems. A dropped request is recoverable; a ledger that is wrong in the wrong direction is not. So most of my design effort goes into what happens on a reorg, a stale price, a duplicated retry, a compromised key — not into the path where everything works.

The decisions below are ones I would defend in a design review. Each of them cost something, and I have tried to say what.

02 — Selected work

Four decisions

And what each one traded away · see all work ↗

01   Reorg-safe event indexer

On-chain data · Settlement
Problem
An indexer that treats a recent block as final is a bug waiting for a reorg. Credit a deposit on data that later disappears and the ledger is wrong in the direction that loses money.
Approach
Verify the parent hash chain on every block rather than trusting block numbers. Store entities keyed by block range so a revert is a delete, not a repair. Tier confirmation policy by value — small amounts credit fast, large amounts wait for finality.
Trade-off
Large deposits settle noticeably slower, and the schema is more complex than a flat table. Accepted deliberately: latency is recoverable, an incorrect balance is not.

02   Automated signing behind a policy engine

Keys · Custody
Problem
A bot that signs without a human in the loop holds a hot key carrying the authority of the whole treasury. Protecting the key is not the same problem as constraining the decision to sign.
Approach
Separate the ability to sign from the authority to sign. A policy layer in front of the signer enforces per-action limits, destination allowlists and rate caps; anything outside policy escalates to a human instead of failing open.
Trade-off
More moving parts, and latency added to every transaction on the path. Bought in exchange: a bounded blast radius when — not if — something is compromised.

03   RPC gateway with head-lag detection

Infrastructure · Reliability
Problem
A single RPC URL is an invisible trust boundary. A provider serving a head from forty minutes ago returns no error — it returns stale truth, and everything downstream acts on it confidently.
Approach
Every service talks to one internal gateway. It probes each upstream's head, marks any source too far behind as lagging, fails over on errors, caps eth_getLogs ranges and allowlists methods. When only stale sources remain it refuses to answer rather than answering wrongly.
Trade-off
An extra hop, plus a component that now has to be operated and monitored itself. Bought: the ability to detect the lie instead of discovering the consequence.

04   AI agent with deterministic guardrails

Agents · Execution
Problem
A language model planning on-chain actions is useful precisely because it is not deterministic — the same reason it cannot be trusted with a signature.
Approach
The model proposes, deterministic code disposes: intent, strategy, quotes across venues, simulation, policy check, then signing. Every step the model touches is replayable, and a model-initiated action passes the same policy layer a human-initiated one would.
Trade-off
The agent is slower and narrower than letting it call tools freely, and much of its output is rejected before execution. That is the design working, not failing.
